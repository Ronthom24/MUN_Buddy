# MUN Buddy - API Standards

## Purpose

This document defines the API design standards for the MUN Buddy backend.

Every API endpoint must follow these standards to ensure consistency, maintainability, security, and ease of integration with the frontend.

The backend follows RESTful architecture.

---

# 1. General Principles

All APIs must:

- Follow REST principles.
- Return JSON responses.
- Use meaningful HTTP status codes.
- Be stateless.
- Validate all incoming data.
- Handle errors gracefully.
- Be versionable if required in the future.

---

# 2. Base URL

Development

```
http://localhost:5000/api
```

Future

```
https://api.munbuddy.com/api
```

Future API versioning may use:

```
/api/v1
/api/v2
```

---

# 3. Resource Naming

Resources should always use plural nouns.

Correct

```
/users
/conferences
/committees
/registrations
/portfolios
/resources
/announcements
```

Avoid:

```
/getConference
/createUser
/deleteCommittee
```

HTTP methods should describe the action.

---

# 4. HTTP Methods

GET

Retrieve data.

POST

Create resources.

PUT

Replace existing resources.

PATCH

Update specific fields.

DELETE

Delete resources.

---

# 5. Standard Success Response

Every successful request should return:

```json
{
    "success": true,
    "message": "Operation completed successfully.",
    "data": {}
}
```

---

# 6. Standard Error Response

Errors should follow a consistent structure.

```json
{
    "success": false,
    "message": "Validation failed.",
    "errors": [
        {
            "field": "email",
            "message": "Email is required."
        }
    ]
}
```

Unexpected server errors:

```json
{
    "success": false,
    "message": "Internal server error."
}
```

Never expose stack traces in production.

---

# 7. HTTP Status Codes

Use standard HTTP status codes.

| Code | Meaning |
|-------|----------|
|200|OK|
|201|Created|
|204|No Content|
|400|Bad Request|
|401|Unauthorized|
|403|Forbidden|
|404|Not Found|
|409|Conflict|
|422|Validation Error|
|429|Too Many Requests|
|500|Internal Server Error|

Avoid using 200 for failed operations.

---

# 8. Authentication

Protected endpoints require JWT authentication.

Header:

```
Authorization: Bearer <token>
```

Authentication middleware should verify:

- Token validity
- Expiration
- User existence

---

# 9. Authorization

Authorization is role-based.

Examples:

Delegates

- View own profile
- Register
- Access approved conferences

Staff

- Manage delegated responsibilities

Organizers

- Full conference management

Authorization should always be enforced on the backend.

---

# 10. Validation

Every endpoint must validate:

- Required fields
- Data types
- Length limits
- Allowed values
- Business rules

Invalid requests should never reach the service layer.

---

# 11. Pagination

Endpoints returning collections should support pagination.

Example:

```
GET /conferences?page=1&limit=20
```

Response:

```json
{
    "success": true,
    "data": [],
    "pagination": {
        "page": 1,
        "limit": 20,
        "total": 135,
        "pages": 7
    }
}
```

---

# 12. Filtering

Filtering should use query parameters.

Example

```
GET /registrations?status=approved
```

Multiple filters:

```
GET /delegates?committee=UNSC&status=approved
```

---

# 13. Sorting

Sorting should use query parameters.

Example

```
GET /conferences?sort=name
```

Descending

```
GET /conferences?sort=-created_at
```

---

# 14. Searching

Search should use:

```
GET /delegates?search=john
```

Search should support partial matching where appropriate.

---

# 15. Route Structure

Examples

Users

```
GET /users

GET /users/:id

POST /users

PATCH /users/:id

DELETE /users/:id
```

Conferences

```
GET /conferences

POST /conferences

GET /conferences/:id

PATCH /conferences/:id

DELETE /conferences/:id
```

Nested resources where appropriate:

```
GET /conferences/:id/committees

GET /committees/:id/portfolios
```

---

# 16. File Uploads

Uploads should use:

```
multipart/form-data
```

Validate:

- MIME type
- Extension
- Maximum file size

Return uploaded file metadata.

---

# 17. Error Handling

Known errors should return meaningful messages.

Examples:

Duplicate email

Conference not found

Registration closed

Portfolio already assigned

Do not expose internal database errors.

---

# 18. Logging

Server logs should include:

- Endpoint
- Method
- User ID (if authenticated)
- Timestamp
- Response status

Sensitive information should never be logged.

---

# 19. Security

Always:

- Use parameterized queries
- Validate input
- Sanitize user input
- Verify JWTs
- Restrict access by role
- Hash passwords
- Rate-limit authentication endpoints

---

# 20. Documentation

Every endpoint should clearly define:

- Purpose
- Method
- URL
- Authentication requirements
- Request body
- Query parameters
- Response examples
- Possible errors

Example:

## Register User

**POST**

```
/api/auth/register
```

Authentication:

None

Request

```json
{
    "name": "John Doe",
    "email": "john@example.com",
    "password": "Password123!"
}
```

Response

```json
{
    "success": true,
    "message": "User registered successfully.",
    "data": {
        "id": 1,
        "email": "john@example.com"
    }
}
```

---

# 21. Future Considerations

The API should be designed to support:

- API versioning
- Rate limiting
- Caching
- Webhooks
- Mobile applications
- Third-party integrations

without requiring major architectural changes.

---

# Guiding Principle

Every API should be:

- Predictable
- Consistent
- Secure
- Well-documented
- Easy to consume
- Easy to maintain

A developer familiar with one endpoint should be able to understand every other endpoint by following these standards.
