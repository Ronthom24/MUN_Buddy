# MUN Buddy - Architecture Decisions

## Purpose

This document records important architectural and technical decisions made during the development of MUN Buddy.

Unlike other documentation, this file explains **why** decisions were made.

Whenever a significant architectural decision is made, it should be recorded here.

This prevents the same discussions from happening repeatedly and provides historical context for future contributors.

---

# Decision Format

Each decision should include:

- ID
- Date
- Status
- Context
- Decision
- Consequences

---

# ADR-001

## Title

Backend Technology Stack

### Status

Accepted

### Context

The backend required a lightweight, scalable framework with strong community support and excellent REST API capabilities.

### Decision

Use:

- Node.js
- Express.js

### Consequences

Advantages:

- Fast development
- Large ecosystem
- Easy deployment
- Excellent MySQL support

Trade-offs:

- Requires disciplined architecture due to JavaScript's flexibility.

---

# ADR-002

## Title

Database Selection

### Status

Accepted

### Context

The application manages highly relational data such as conferences, committees, registrations, assignments, and users.

### Decision

Use MySQL.

### Consequences

Advantages:

- Strong relational model
- Mature ecosystem
- Excellent indexing
- Reliable transactions

---

# ADR-003

## Title

Authentication Strategy

### Status

Accepted

### Context

The backend should remain stateless.

### Decision

Use JWT authentication with bcrypt password hashing.

### Consequences

Advantages:

- Stateless authentication
- Easy mobile integration
- Good scalability

Future Improvements:

- Refresh Tokens
- MFA

---

# ADR-004

## Title

Backend Architecture

### Status

Accepted

### Context

Business logic should remain separated from HTTP concerns.

### Decision

Adopt a layered architecture.

Routes

↓

Controllers

↓

Services

↓

Models

↓

Database

### Consequences

Improved maintainability and testability.

---

# ADR-005

## Title

Frontend Framework

### Status

Accepted

### Context

The application requires a single codebase for Android and iOS.

### Decision

Use Flutter.

### Consequences

Advantages:

- Cross-platform
- High performance
- Strong Material Design support

---

# ADR-006

## Title

API Design

### Status

Accepted

### Decision

Adopt RESTful APIs using JSON.

### Consequences

Easy frontend integration and future extensibility.

---

# ADR-007

## Title

Database Philosophy

### Status

Accepted

### Decision

Normalize data and enforce relationships using foreign keys.

### Consequences

Improved consistency and reduced duplication.

---

# ADR-008

## Title

Project Development Strategy

### Status

Accepted

### Decision

Develop the platform feature-by-feature rather than module-by-module.

Each feature should:

- Be complete
- Be tested
- Be documented

before moving on.

### Consequences

Improved stability and easier debugging.

---

# ADR-009

## Title

Code Quality

### Status

Accepted

### Decision

Only production-ready code should be committed.

Prototype implementations are not acceptable unless explicitly requested.

### Consequences

Higher initial development effort but significantly improved maintainability.

---

# ADR-010

## Title

Documentation

### Status

Accepted

### Decision

Maintain project documentation alongside the codebase.

Every major architectural change should update the relevant documentation.

### Consequences

Better onboarding and reduced knowledge loss.

# Guiding Principle

Architecture decisions should be deliberate, documented, and revisited only when requirements change significantly.

Avoid changing established decisions without a clear technical or business justification.
