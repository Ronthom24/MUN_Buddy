# MUN Buddy - Authentication & Authorization Flow

## Purpose

This document defines how authentication and authorization work throughout the MUN Buddy platform.

Authentication verifies the identity of a user.

Authorization determines what an authenticated user is allowed to access.

Every protected feature in the application must follow these standards.

---

# Authentication Overview

MUN Buddy uses JSON Web Tokens (JWT) for stateless authentication.

Passwords are never stored in plain text.

All passwords are securely hashed before being saved to the database.

Authentication consists of four major stages:

1. Registration
2. Login
3. Token Verification
4. Authorization

---

# User Registration Flow

Registration follows this sequence.

```
User

↓

Register Screen

↓

Validation

↓

Backend API

↓

Hash Password

↓

Save User

↓

Success Response
```

### Steps

1. User enters registration details.

2. Frontend validates basic input.

3. Backend validates all fields.

4. Email uniqueness is checked.

5. Password is hashed using bcrypt.

6. User record is inserted.

7. Success response returned.

---

# Login Flow

```
User

↓

Login Screen

↓

Backend

↓

Find User

↓

Verify Password

↓

Generate JWT

↓

Return Token

↓

Store Securely

↓

Authenticated Session
```

### Steps

1. User enters email and password.

2. Backend retrieves the user.

3. Password is verified.

4. JWT is generated.

5. JWT returned to frontend.

6. Token stored securely.

7. User redirected to application.

---

# JWT Structure

The JWT should contain only necessary information.

Example payload:

```
User ID

Email

Role

Issued Time

Expiration Time
```

Sensitive information must never be stored inside the token.

---

# Token Storage

Frontend should store JWT securely.

Never store authentication tokens inside:

- Source code
- URLs
- Logs

Authentication tokens should be removed immediately during logout.

---

# Authenticated Requests

Every protected request should include:

```
Authorization: Bearer <JWT_TOKEN>
```

Backend middleware verifies:

- Token validity
- Expiration
- User existence

Only then should the request continue.

---

# Logout Flow

Logout consists of:

1. Remove stored JWT.
2. Clear user session.
3. Redirect to Login.

Future versions may include token blacklisting if refresh tokens are introduced.

---

# Authorization

Authentication answers:

"Who is this user?"

Authorization answers:

"What can this user do?"

Both must always be enforced.

---

# User Roles

Current roles:

- Organizer
- Staff
- Delegate

Future roles:

- Admin
- Judge
- Observer

The authorization system should support future expansion without major changes.

---

# Organizer Permissions

Organizers can:

- Create conferences
- Edit conferences
- Delete conferences
- Manage staff
- Create committees
- Create portfolios
- Review registrations
- Assign delegates
- Upload resources
- Publish announcements
- Generate certificates
- View analytics

---

# Staff Permissions

Staff permissions are granted by organizers.

Possible permissions include:

- Review registrations
- Manage committees
- Upload resources
- Publish announcements
- Assign portfolios

Permission granularity should be expandable.

---

# Delegate Permissions

Delegates can:

- Register
- Login
- Update profile
- Register for conferences
- View approved conferences
- Download resources
- View announcements
- Download certificates

Delegates must never access organizer-only functionality.

---

# Protected Routes

Protected routes require:

Valid JWT

+

Required Role

Example:

```
Organizer

↓

Create Conference
```

```
Delegate

↓

Register Conference
```

If authorization fails:

Return HTTP 403 Forbidden.

---

# Public Routes

Examples:

Login

Register

Forgot Password (Future)

Reset Password (Future)

Health Check

Public conference listing (Optional)

---

# Session Expiration

JWTs should expire after a configurable duration.

Expired tokens require re-authentication.

Future implementations may introduce refresh tokens.

---

# Password Security

Passwords should:

- Be hashed using bcrypt.
- Never be logged.
- Never be returned by APIs.
- Never be stored in plaintext.

Minimum password policy should include:

- Minimum length
- Uppercase letter
- Lowercase letter
- Number
- Special character

---

# Account Recovery (Future)

Future features:

Forgot Password

↓

Email Verification

↓

Password Reset Token

↓

Reset Password

Tokens should expire after a short duration.

---

# Email Verification (Future)

Future implementation may require:

Account Creation

↓

Verification Email

↓

Verification Link

↓

Account Activated

---

# Security Considerations

Authentication should protect against:

- Brute-force attacks
- Credential stuffing
- Token tampering
- SQL Injection
- Unauthorized access

Future versions may introduce:

- Rate limiting
- Multi-factor authentication
- Device management

---

# Error Responses

Authentication failures should never reveal unnecessary information.

Instead of:

"Email not found"

Use:

"Invalid email or password."

This prevents user enumeration.

---

# Future Improvements

Possible future enhancements:

- Refresh Tokens
- Multi-Factor Authentication (MFA)
- OAuth Login
- Google Sign-In
- Apple Sign-In
- Session Management
- Active Device List

The architecture should support these features without requiring major redesign.

---

# Guiding Principles

Authentication should always be:

- Secure
- Stateless
- Simple
- Scalable
- Maintainable

Authorization should always be enforced on the backend.

The frontend may hide UI elements for convenience, but it must never be trusted to enforce access control.
