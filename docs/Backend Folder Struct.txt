# MUN Buddy - Backend Folder Structure

## Purpose

This document defines the organization of the MUN Buddy backend project.

Every directory has a single responsibility. New files should always be placed in the appropriate location to maintain a clean, scalable, and maintainable architecture.

---

# Project Structure

```
backend/

├── src/
│   ├── config/
│   ├── controllers/
│   ├── middleware/
│   ├── models/
│   ├── routes/
│   ├── services/
│   ├── validators/
│   ├── utils/
│   ├── database/
│   ├── uploads/
│   ├── app.js
│   └── server.js
│
├── tests/
│
├── package.json
├── package-lock.json
├── .env.example
└── README.md
```

---

# src/

The `src` directory contains all application source code.

Everything required to run the backend should exist inside this directory.

---

# config/

Purpose:

Application configuration.

Examples:

- Database configuration
- JWT configuration
- Environment variables
- Multer configuration
- Application constants

Rules:

- No business logic.
- Only configuration.

---

# controllers/

Purpose:

Controllers receive HTTP requests.

Responsibilities:

- Read request data
- Call services
- Return HTTP responses

Controllers should remain lightweight.

They should never contain business logic.

---

# services/

Purpose:

Contains business logic.

Responsibilities:

- Implement application rules
- Coordinate multiple database operations
- Execute transactions
- Process data

Services should not know anything about HTTP.

---

# models/

Purpose:

Represent database entities.

Responsibilities:

- Execute database queries
- Interact with MySQL
- Return structured data

Models should not implement business rules.

---

# routes/

Purpose:

Define API endpoints.

Responsibilities:

- Register endpoints
- Apply middleware
- Forward requests to controllers

Routes should never contain business logic.

---

# middleware/

Purpose:

Shared request-processing logic.

Examples:

- JWT authentication
- Authorization
- Validation
- Error handling
- Logging
- Rate limiting

Middleware should be reusable.

---

# validators/

Purpose:

Validate incoming request data.

Examples:

- Register validation
- Login validation
- Conference validation
- Committee validation

Validation should happen before controllers execute business logic.

---

# utils/

Purpose:

Reusable helper functions.

Examples:

- Password hashing
- JWT generation
- Date formatting
- File helpers
- Response helpers

Utilities should remain generic.

---

# database/

Purpose:

Database-related utilities.

Examples:

- Connection pool
- Database initialization
- Transactions
- Query helpers

This folder should not contain business logic.

---

# uploads/

Purpose:

Temporary storage for uploaded files.

Examples:

- Background Guides
- Position Papers
- Profile Pictures

Files should be validated before storage.

Future versions may replace local storage with cloud storage.

---

# tests/

Purpose:

Automated tests.

Future structure:

```
tests/

unit/

integration/

fixtures/
```

Tests should never modify production data.

---

# app.js

Purpose:

Configure the Express application.

Responsibilities:

- Register middleware
- Configure routes
- Configure error handling

Do not start the server here.

---

# server.js

Purpose:

Application entry point.

Responsibilities:

- Load environment
- Connect database
- Start Express server

Nothing else.

---

# File Placement Guidelines

When creating a new feature:

Routes

↓

Controllers

↓

Services

↓

Models

↓

Validators (if required)

↓

Utilities (if reusable)

Every file should have a clearly defined responsibility.

---

# Dependency Rules

Allowed dependencies:

```
Routes

↓

Controllers

↓

Services

↓

Models

↓

Database
```

Not allowed:

- Controllers importing routes
- Services importing controllers
- Models importing services

Dependencies should always point downward.

---

# Naming Conventions

Folders:

lowercase

Files:

Descriptive

Examples:

```
auth.controller.js

auth.service.js

auth.routes.js

user.model.js

jwt.middleware.js
```

Avoid abbreviations.

---

# Scalability

The folder structure should support future modules including:

- Messaging
- Payments
- Notifications
- Certificates
- Analytics
- AI Services

without requiring significant restructuring.

---

# Guiding Principles

Every file should have:

- One responsibility
- One clear purpose
- One logical location

If a file seems to belong in multiple folders, reconsider its design.

Maintain consistency throughout the project to ensure long-term maintainability.
