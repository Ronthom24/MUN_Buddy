# MUN Buddy - State Management

## Purpose

This document defines how application state should be managed throughout the MUN Buddy Flutter application.

The primary goals are:

- Predictability
- Scalability
- Maintainability
- Performance
- Separation of concerns

The frontend should remain responsible only for UI state and presentation. Business logic and data validation belong on the backend.

---

# Core Principles

The application should maintain a single, consistent state management approach.

Avoid mixing multiple state management solutions throughout the project.

Every screen should follow the same architectural pattern.

---

# Types of State

Application state can be divided into four categories.

---

## 1. Local UI State

Local state belongs only to a single widget.

Examples:

- Password visibility
- Selected tab
- Current page
- Search text
- Checkbox state
- Form field focus
- Expansion tiles

Local state should not be shared with other screens.

---

## 2. Feature State

Feature state belongs to a single feature.

Examples:

Authentication

Conference List

Registration Form

Committee Details

Announcements

Resources

Feature state should remain isolated from unrelated modules.

---

## 3. Global Application State

Global state is shared across the application.

Examples:

Current User

Authentication Status

Theme

Language

Permissions

Conference currently selected

Only data required by multiple screens should become global.

---

## 4. Temporary State

Temporary state exists only while performing an operation.

Examples:

Loading

Uploading

Downloading

Saving

Deleting

Validation

Temporary state should never be permanently stored.

---

# Separation of Responsibilities

The UI should only display data.

State management should coordinate:

- Loading
- Refreshing
- Error handling
- Data updates

Business rules remain on the backend.

---

# Data Flow

The application should follow a predictable flow.

```
UI

↓

State

↓

Service

↓

REST API

↓

Backend

↓

JSON Response

↓

State Update

↓

UI Refresh
```

Data should always flow in one direction.

---

# Single Source of Truth

Every piece of application data should have one authoritative source.

Example:

Current user information should exist in one place.

Multiple copies of the same data should be avoided.

---

# Loading States

Every network request should expose loading state.

Examples:

Loading Conference

Loading Committees

Loading Resources

Submitting Registration

The UI should react automatically.

---

# Error States

Errors should be represented as state.

Examples:

Network Error

Validation Error

Authentication Error

Server Error

The UI should present meaningful feedback.

---

# Success States

Successful operations should update state.

Examples:

Conference Created

Registration Submitted

Portfolio Assigned

Announcement Published

UI should immediately reflect updated information.

---

# Refresh Strategy

Data should refresh when:

- User performs pull-to-refresh.
- Important actions complete.
- User returns to a screen when appropriate.

Avoid unnecessary repeated API calls.

---

# Caching

Frequently used data may be cached.

Examples:

Current User

Conference List

Committees

Settings

Cached data should always be refreshable.

---

# Authentication State

Authentication should maintain:

Current User

JWT Token

Login Status

User Role

Authentication state should initialize during application startup.

---

# Form State

Forms should manage:

Field Values

Validation

Loading

Submission Status

Errors

Form state should reset appropriately after successful submission.

---

# Search State

Search should maintain:

Current Query

Search Results

Loading State

Filters

Sorting

Pagination

Search should not permanently modify stored data.

---

# Pagination State

Lists should track:

Current Page

Total Pages

Loading More

Has More Data

Pagination should support infinite scrolling where appropriate.

---

# Optimistic Updates

Use optimistic UI updates only when appropriate.

Examples:

Mark Notification Read

Bookmark Item

Like Action

Critical operations should wait for backend confirmation.

---

# Offline Considerations

Future versions may support:

Cached data

Offline viewing

Queued requests

Conflict resolution

Current implementation assumes network connectivity.

---

# Performance

Avoid unnecessary widget rebuilds.

Avoid storing large datasets in memory.

Dispose resources when no longer needed.

Keep state as small as possible.

---

# Security

Never store:

Passwords

Sensitive personal data

API secrets

Authentication tokens should be stored securely.

---

# Testing

State management should be easy to test.

Business logic should not depend on UI widgets.

State should remain predictable under all conditions.

---

# Future Expansion

The chosen architecture should support:

Push Notifications

Offline Mode

Background Sync

Real-time Updates

Multi-language Support

Desktop Support

without significant redesign.

---

# Guiding Principles

State should always be:

- Predictable
- Minimal
- Reusable
- Easy to debug
- Easy to test
- Independent of UI implementation

A user action should always produce a clear, understandable, and consistent state transition.
