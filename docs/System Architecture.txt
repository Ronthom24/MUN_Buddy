# MUN Buddy - System Architecture

## Purpose

This document describes the architectural design of the MUN Buddy platform.

It explains how different parts of the application interact, the responsibilities of each layer, and the architectural principles that must be followed throughout development.

This document should be treated as the authoritative reference for architectural decisions.

---

# Architecture Philosophy

MUN Buddy follows a modular layered architecture.

The primary goals are:

- Separation of concerns
- Scalability
- Maintainability
- Testability
- Reusability
- Security

Every component should have a single, clearly defined responsibility.

Business logic should remain independent from transport mechanisms and database implementation wherever practical.

---

# High-Level Architecture

```

Flutter Application
│
▼
REST API (Express.js)
│
▼
Routes
│
▼
Controllers
│
▼
Services
│
▼
Database Layer
│
▼
MySQL Database

```

Each layer has a dedicated responsibility and communicates only with adjacent layers.

---

# Backend Layer Responsibilities

## Routes

Responsibilities:

- Define API endpoints
- Apply middleware
- Forward requests to controllers

Routes should never contain business logic.

---

## Controllers

Responsibilities:

- Receive requests
- Extract request data
- Call services
- Return responses
- Handle HTTP concerns

Controllers should remain lightweight.

Business logic should never be placed inside controllers.

---

## Services

Services contain the application's business logic.

Responsibilities include:

- Processing requests
- Validating business rules
- Performing calculations
- Coordinating database operations
- Managing transactions

Services should be reusable and independent of HTTP.

---

## Database Layer

Responsibilities:

- Execute SQL queries
- Return database results
- Maintain consistency

Business rules should generally not live here.

---

## Middleware

Middleware handles cross-cutting concerns.

Examples:

- JWT Authentication
- Authorization
- Validation
- Logging
- Error handling
- Rate limiting

Middleware should remain generic and reusable.

---

## Utilities

Utility modules contain reusable helper functions.

Examples:

- Password hashing
- JWT generation
- Date formatting
- File handling

Utilities should not contain business logic.

---

# Frontend Architecture

The Flutter application should be organized into independent feature modules.

Typical responsibilities include:

- UI
- Navigation
- API communication
- State management
- Local storage

Business rules should primarily reside on the backend.

The frontend should never enforce security rules.

---

# Request Lifecycle

Every request follows the same path.

Client Request

↓

Route

↓

Middleware

↓

Controller

↓

Service

↓

Database

↓

Service

↓

Controller

↓

JSON Response

Each layer should only perform its designated responsibility.

---

# Authentication Flow

1. User registers.
2. Password is hashed.
3. User record is stored.
4. User logs in.
5. Credentials are verified.
6. JWT is generated.
7. Client stores token.
8. Protected requests include:

Authorization: Bearer <token>

9. Middleware verifies token.
10. Request proceeds if authorized.

---

# Authorization

Authorization is role-based.

Examples:

Delegate

↓

Delegate Routes

Organizer

↓

Organizer Routes

Staff

↓

Staff Routes

Every protected endpoint must verify permissions before executing business logic.

---

# Database Communication

Controllers should never execute SQL.

Services coordinate data operations.

Database modules execute parameterized queries.

This separation improves maintainability and testability.

---

# Folder Responsibilities

Example backend structure:

src/

config/

controllers/

middleware/

models/

routes/

services/

utils/

validators/

uploads/

Each folder should have one clear purpose.

Avoid mixing responsibilities.

---

# Error Flow

Errors should propagate through a centralized error handling mechanism.

Unexpected exceptions should:

- Be logged
- Return generic responses
- Never expose implementation details

Validation errors should return meaningful messages.

---

# Validation Strategy

Validation occurs before business logic.

Incoming requests should be validated for:

- Required fields
- Data types
- Formats
- Length
- Business constraints

Invalid requests should never reach the service layer.

---

# Security Architecture

Security should be enforced at multiple layers.

Examples:

Input Validation

↓

Authentication

↓

Authorization

↓

Database Protection

↓

Output Sanitization

Never trust client input.

---

# Database Design Principles

The database should remain:

- Normalized
- Consistent
- Extensible

Relationships should use foreign keys.

Duplicate data should be minimized.

---

# Scalability Strategy

The architecture should support:

- Multiple conferences
- Multiple organizers
- Thousands of delegates
- Large datasets
- Future modules

Future features should integrate without requiring architectural redesign.

---

# Dependency Rules

Dependencies should flow inward.

Example:

Routes

↓

Controllers

↓

Services

↓

Database

Lower layers should never depend on higher layers.

Controllers should never import routes.

Services should never import controllers.

---

# Code Organization Principles

Every module should:

- Have one responsibility
- Be reusable
- Be easy to understand
- Be independently testable

Avoid circular dependencies.

Avoid tightly coupled components.

---

# Future Architecture

The architecture should remain flexible enough to support:

- Notifications
- Email services
- File storage services
- Cloud deployment
- AI-powered features
- Payments
- Mobile applications
- Admin dashboards

without major restructuring.

---

# Guiding Principles

Every architectural decision should prioritize:

- Simplicity
- Maintainability
- Security
- Scalability
- Performance
- Consistency

The goal is to build a backend that remains clean and maintainable as the project grows over time.
