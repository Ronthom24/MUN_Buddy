# MUN Buddy - Testing Guidelines

## Purpose

This document defines the testing strategy for the MUN Buddy platform.

Every feature implemented should be tested before being considered complete.

Testing ensures reliability, maintainability, and prevents regressions as the application grows.

---

# Testing Philosophy

Every feature should be:

- Verified manually
- Designed for automated testing
- Tested against edge cases
- Tested against invalid input

Testing is part of development, not an afterthought.

---

# Testing Levels

The project uses multiple levels of testing.

## 1. Unit Testing

Tests individual functions and business logic.

Examples:

- Password hashing
- JWT generation
- Validation
- Utility functions
- Service methods

Unit tests should be independent of the database.

---

## 2. Integration Testing

Tests interaction between multiple components.

Examples:

- API ↔ Database
- Controller ↔ Service
- Authentication middleware
- Registration workflow

Integration tests verify complete feature functionality.

---

## 3. API Testing

Every endpoint should be tested.

Verify:

- Status Codes
- Response Format
- Validation
- Authentication
- Authorization
- Error Handling

Postman or Bruno collections should be maintained.

---

## 4. Frontend Testing

Flutter tests should verify:

- Widget rendering
- Navigation
- Form validation
- Loading states
- Error states
- User interactions

---

## 5. End-to-End Testing

Critical user journeys should be tested.

Examples:

- Register
- Login
- Create Conference
- Register for Conference
- Assign Portfolio
- Upload Resource

---

# Manual Testing Checklist

For every completed feature verify:

- Happy path works.
- Invalid input is rejected.
- Unauthorized access is blocked.
- Errors display correctly.
- Database updates correctly.
- UI updates correctly.
- No console errors.

---

# Backend Testing

Every API should be tested for:

## Success

Expected behaviour.

## Validation

Missing fields

Invalid formats

Duplicate values

Business rule violations

## Authentication

No JWT

Expired JWT

Invalid JWT

## Authorization

Wrong role

Unauthorized resource access

## Database

Successful insert

Successful update

Successful delete

Transaction rollback

---

# Frontend Testing

Verify:

- Responsive layouts
- Navigation
- Form validation
- Loading indicators
- Error messages
- Empty states
- API integration

---

# Regression Testing

Whenever a feature changes:

Verify previously working functionality.

Never assume unrelated features still work.

---

# Performance Testing

Monitor:

- API response time
- Database query efficiency
- UI responsiveness
- Loading speed

Avoid unnecessary API calls.

---

# Security Testing

Verify:

- SQL Injection prevention
- JWT validation
- Password hashing
- Authorization rules
- File upload validation

---

# Error Handling

Every feature should be tested for:

- Invalid requests
- Missing resources
- Server errors
- Network failures
- Database failures

The application should fail gracefully.

---

# Definition of Done

A feature is complete only when:

- Requirements are implemented.
- Code is production-ready.
- Validation is complete.
- Error handling is implemented.
- Manual testing passes.
- Documentation is updated.
- No known critical issues remain.

---

# Guiding Principle

Every feature should leave the project in a more stable state than before it was implemented.

Quality is measured not only by functionality but also by reliability, maintainability, and robustness.
