# MUN Buddy - Business Rules

## Purpose

This document defines the business rules that govern the MUN Buddy platform. These rules describe how the application should behave from a functional perspective and must always take precedence over implementation assumptions.

If a business rule is unclear or missing, clarification should be requested before implementation.

---

# 1. Users

## User Roles

The platform currently supports three primary roles:

- Organizer
- Staff
- Delegate

Future roles (e.g., Admin or Judge) may be introduced without requiring major architectural changes.

---

## Organizer

Organizers can:

- Create conferences
- Edit conferences
- Delete conferences
- Manage staff
- Create committees
- Create portfolios
- Review delegate registrations
- Assign delegates
- Upload resources
- Publish announcements
- Generate certificates
- View analytics

An organizer has complete administrative control over conferences they own.

---

## Staff

Staff members assist organizers.

Permissions are assigned by organizers.

Examples:

- Review registrations
- Manage committees
- Assign portfolios
- Upload resources
- Publish announcements

Staff permissions should be configurable in the future.

---

## Delegates

Delegates can:

- Register an account
- Join conferences
- Submit applications
- Upload required documents
- View application status
- Access conference resources
- View schedules
- Receive announcements
- Download certificates

Delegates cannot perform administrative actions.

---

# 2. Conferences

A conference is the highest-level entity.

Every committee belongs to exactly one conference.

Every registration belongs to exactly one conference.

Every announcement belongs to exactly one conference.

Conference names do not have to be globally unique.

Only organizers can create conferences.

---

## Conference Lifecycle

A conference progresses through stages such as:

- Draft
- Registration Open
- Registration Closed
- Ongoing
- Completed
- Archived

Only organizers should be able to change conference status.

---

# 3. Registrations

A delegate may submit only one active registration per conference.

Rejected delegates may submit another registration if organizers allow re-registration.

Registration status includes:

- Pending
- Approved
- Waitlisted
- Rejected

Registration history should be preserved.

---

# 4. Committees

Each committee belongs to one conference.

Committee names only need to be unique within the same conference.

Examples:

UNSC may exist in multiple conferences.

Committees may define:

- Name
- Description
- Capacity
- Chair information

---

# 5. Portfolios

Each portfolio belongs to one committee.

Portfolio names only need to be unique within their committee.

Examples:

USA may exist in multiple committees.

France may exist in multiple conferences.

A portfolio may only be assigned to one delegate at a time.

---

# 6. Delegate Assignments

Approved delegates may receive:

- Committee assignment
- Portfolio assignment

Each delegate should have only one active committee assignment per conference unless future requirements specify otherwise.

Portfolio assignments must remain unique.

---

# 7. Resources

Resources belong to either:

- Conference
- Committee

Examples:

- Background Guides
- Study Guides
- Schedules
- Rulebooks

Only organizers and authorized staff can upload resources.

Delegates may only access resources for conferences in which they are approved.

---

# 8. Announcements

Announcements may target:

- Entire conference
- Individual committee

Delegates should only receive announcements relevant to their conference or committee.

Announcement history should remain accessible.

---

# 9. Certificates

Certificates may only be generated after a conference has concluded.

Delegates should only be able to access their own certificates.

Certificate generation should be repeatable without creating duplicate records.

---

# 10. Payments (Future)

If registration fees are enabled:

- Each registration should track payment status.
- Payment verification should occur before approval when required.
- Transactions should be auditable.

---

# 11. Authentication

Every user account requires:

- Name
- Email
- Password

Passwords must always be securely hashed.

Email addresses must be unique across the platform.

JWT authentication will secure protected APIs.

---

# 12. Authorization

Users may only access resources permitted by their role.

Examples:

Delegates cannot edit conferences.

Staff cannot manage conferences unless granted permission.

Organizers only manage conferences they own.

---

# 13. File Uploads

Supported uploads may include:

- Profile pictures
- Position papers
- Background guides
- Conference documents
- Certificates

Uploaded files should be validated for:

- File type
- File size
- Storage location

---

# 14. Notifications

Future versions may include:

- Email notifications
- In-app notifications
- Push notifications

Notification logic should be modular and easily extensible.

---

# 15. Analytics

Organizers should be able to view:

- Registration counts
- Approval rates
- Committee occupancy
- Delegate statistics

Analytics must never expose private delegate information.

---

# 16. Data Integrity

The system should maintain referential integrity at all times.

Examples:

- A committee cannot exist without a conference.
- A portfolio cannot exist without a committee.
- A registration cannot exist without a conference.
- A delegate cannot receive two assignments for the same portfolio.

---

# 17. Auditability

Important actions should be traceable.

Examples:

- Registration approval
- Portfolio assignment
- Conference creation
- Resource uploads
- Announcement publication

Future audit logs should record:

- User
- Action
- Timestamp

---

# 18. Scalability

The platform should support:

- Multiple organizers
- Multiple simultaneous conferences
- Thousands of delegates
- Hundreds of committees

Business rules should never assume only one conference exists.

---

# 19. Future Extensibility

Future features should integrate without requiring major redesign.

Examples include:

- Judge Portal
- Crisis Committees
- AI-powered features
- QR Attendance
- Mobile notifications
- Live voting
- Integrated payments

The architecture should remain flexible enough to accommodate these additions.
